# 指令前置自己打核心补丁（启用时打、停用时摘、启动时自愈）

**Status**: accepted

这个插件要在会话诞生之前接管消息，就必须在核心消息入口留调用点（见 ADR 0003）。而调用点一旦被上游新版覆盖就会消失，症状是"插件装了、启用了，但发指令毫无反应" —— 用户几乎不可能自己想到去照 UPGRADE.md 手工重打。我们决定让插件在**启用时（含每次软件启动、每次重扫插件）自动检查并补上**这些调用点，在**停用时按标记精确摘除**，并把这个状态写进设置页。补丁以标记块形式插入（`[[command-gateway:<id>]] … [[/command-gateway:<id>]]`），代码本体放在插件目录的 `patches/` 下。

## Considered Options

- 只保留手工补丁清单（UPGRADE.md）：升级后必然有一段时间"看起来是插件坏了"，而且没人会记得来看这份文件。
- 把指令系统做进核心：那就不是插件了，每加一条指令都要改核心。
- 让核心提供通用的"消息入口事件"给插件订阅：核心里要加的东西比现在这几处薄调用点多得多，反而更侵入；而且事件点的时序（必须早于存档、且要能自己发消息）还是要核心专门设计。
- 自动打补丁 + 标记块（本决策）：核心侧的改动仍然只有那几处，但维护成本从"记得手工重打"变成"`patch.mjs` 自己打"，代价是插件会写用户的源码文件。

## Consequences

- **插件会写 `src/`、`ui/`、`electron/` 里的文件**。这是刻意的：不这么做就没有自愈。三条约束把风险压住 —— 锚点找不到就一个文件都不写（原子）、标记块可精确摘除、文件被外部改过时**不拿旧备份覆盖**（上游升级优先于回滚，见 ADR 0003 讨论过的取舍）。
- 打完补丁**必须重启软件**才生效（改的是已经加载进内存的文件）。设置页顶部会明确写出"需要重启软件才生效"，否则用户会把"没生效"当成"插件坏了"。
- 热重载（保存插件文件）会触发 `deactivate({reason:'reload'})`，那种情况**不摘补丁**，否则每次保存都在核心文件里摘一次再打一次。
- 备份与状态留在插件目录（`backup/`），停用也不删：冲突时它是唯一的"原件"。备份只在首次打补丁时生成，避免第二次备份到的其实是"打过补丁的版本"。
- 界面一并搬进了插件（`settings-ui.js` + 核心的通用挂载点），所以这份补丁清单不会再随界面改动变长。
