# 热重载的边界：哪些热、哪些必须重启、boot-heal 把自愈提到核心加载前

**Status**: accepted（2026-09-28，v1.7.0）

「指令前置」一直被一条警告缠着：**启用后要重启软件才生效**。0.4.x 核心引入插件热重载
（`watchPlugins` + 带时间戳的动态 import）之后，用户自然 expectation 变成"改什么都应该热生效"。
我们把热重载的边界说清楚，并把唯一剩下的"必须重启"场景尽量压短：

- **热生效**（无需重启）：插件代码改动（`index.js` / `services.js` / 指令实现 / 设置页）——
  核心 watcher 触发重扫，模块带 `?t=` 重新 import；启用/停用开关——消息入口的调用点
  每条消息**现场**查 `getCapabilityProviders('command.dispatch')`，不缓存提供者。
- **必须重启一次**：核心补丁块的**首次打入**与**内容升级**。调用点是写进 `src/app.js` 的
  代码，进程把旧代码加载进内存后就改不动了 —— 这是 ESM 的边界，不是工程取舍。
- **boot-heal**：上游升级覆盖核心文件后，原流程是「重启 → activate 自愈发现缺块 → 再重启」
  两轮。现在 `electron/main.js` 在 `import('../src/app.js')` **之前**见到启用旗标
  （`patch-on-boot.flag`，启用时写、停用时摘）就跑一次 `apply()`，两轮并成一轮，
  且保证补丁先于核心代码生效。

## Considered Options

- 维持现状（所有补丁动作都要重启一次自愈）：上游升级后用户要重启两次，且第一轮里
  指令系统整体失联，症状像"插件坏了"。
- 把调用点改成 `globalThis` 注册表 + 一次性永久 shim：能让"块内容永不升级"成立，
  但 payload 构造引用调用点作用域的局部变量（`text` / `atMe` / `event`…），核心重构
  作用域照样要升级块 —— 复杂度换了不多少收益，放弃。
- boot-heal 无条件每次启动 `apply()`：停用后的插件会在下次启动被自动打回补丁，
  违反"停用即还原"的承诺。所以用旗标文件把"用户启用过"显式记下来。
- boot-heal 从核心 config.json 读启用状态：让补丁引擎依赖核心配置格式，
  与 LEGACY_IDS 迁移纠缠，脆。旗标文件跟着插件目录走，零依赖。

## Consequences

- 用户视角的规则变成一句话：**装好后启用 → 重启一次 → 以后随便折腾（除非上游又改了核心）**。
- 旗标文件在插件目录里，会被热重载 watcher 看到 —— activate 写旗标必须幂等
  （已存在就不写），否则"写旗标 → 重扫 → activate → 写旗标"会转起来。
- boot-heal 块按 `optional` 声明：headless（无桌面壳）部署没有那个 import 语句，
  跳过即可，activate 时的启动自愈仍然兜底（只是要多一轮重启）。
- 停用后旗标被摘，boot-heal 不会再把补丁打回来 —— "停用即还原"不受影响。
  摘除失败（冲突）时旗标保留：文件里可能还留着补丁块，下次启动还要能自愈。
