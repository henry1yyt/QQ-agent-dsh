# 指令前置采用核心薄调用点 + 插件全实现

**Status**: accepted

指令要"在会话诞生之前拦截、并且能自己发消息"，而插件体系原有的钩子最早也在会话创建之后，且被明确禁止发消息、发请求。我们决定在核心消息入口（`src/app.js` 的 `ingestMessage`）加一个薄调用点：核心取 `command.dispatch` 能力，插件同步返回是否认领；认领则这条消息不存档、不建会话，异步执行放进返回的 `run()` 里 fire-and-forget，消息热路径不等待。其余全部由 `command-gateway` 插件实现：解析、权限、冷却、路由、回执、调用记录。子插件按 `manifest.command` 声明元信息并提供 `command.<id>` 能力接入；核心只多做两件小事——清单保留 `command` 字段、插件列表把它透出。审计脚本增加一条规则：被 `command` 声明过的能力由指令前置消费，不算孤儿能力。

## Considered Options

- 纯插件复用现有钩子：`before-context` 等钩子发生在会话创建之后，而且被禁止发消息，做不到"会话不诞生 + 即时回执"。
- 插件自行监听消息 / import 核心入口：消息入口没有对插件开放的事件，插件拿不到"未存档的原始消息"，也绕过了核心边界。
- 把指令系统做进核心：插件无法参与，违背"扩展而不是内置"的方向；每加一条指令都要改核心。
- 核心薄调用点 + 插件全实现（本决策）：核心只多约二十行加两个字段透出；代价是核心升级后需要按插件目录内的补丁说明重打，与 `enhanced-impression` 的 `UPGRADE.md` 模式一致。

## Consequences

- 不启用 `command-gateway` 时，核心调用点取不到能力提供者，行为与旧版本完全一致（每条消息只多一次能力查询）。
- 指令消息不存档、不产生会话记录，所以会话页看不到指令调用；最近调用记录由插件写回自己的配置段（`config.skills['command-gateway']`），UI 的设置子页面从那里读取。这也是本插件 import 核心 `config.js` 的唯一原因。
- 子插件的执行能力必须是 async：只有 Promise 才能被前置插件的超时竞争与错误捕获正确接管。
