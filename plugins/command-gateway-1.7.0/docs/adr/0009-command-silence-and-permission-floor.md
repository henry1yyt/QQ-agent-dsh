# 指令静默：窗口与封锁共用一个时长，计数只算真正执行的

同一个 QQ 在一个**静默期**内用掉「触发次数」条指令（默认 10 秒 / 3 条，元指令也算）之后，
接下来一个静默期他不能用任何指令 —— 目的不是惩罚，而是让"连点刷屏"这条路径不再占用模型与协议端资源。
我们决定：**静默时间既当滑动统计窗口、也当封锁时长**（一个值，不是两个）；
**第 N 次照常执行**，封锁从那一刻算起；**触发时清空窗口**，解封后从 0 开始。

同时放开权限下限：权限表（含「默认权限」行）可以填 **-1 = 一律禁止使用任何指令**。
它**必须显式判断**（`level <= PERM_MIN`），不能只靠 `触发者等级 ≥ 指令等级` ——
否则 `-1 ≥ -1` 成立，一条同样被设成 -1 的指令会被他钻过去。指令等级本身仍然一律 ≥ 0。

## Considered Options

- **窗口与封锁共用一个值（选定）**。用户只填一个数、只有一个概念；"10 秒内刷 3 条就安静 10 秒"读起来也是人话。
  代价：想表达"长窗口、短封锁"就做不到 —— 但那是运营策略，不是防刷的需求；真需要时再加第二个字段，不预先付这个复杂度。
- **窗口与封锁分成两个字段**。表达力更强，但设置页要解释两个数的乘积语义，作者自己也说不清"5 分钟窗口封 10 秒"到底想干嘛。否掉。
- **触发时保留窗口（不清空）**。解封后第一条会立刻再次触发静默 → 连环封，表现成"解封了但一个都发不出来"。
  作者明确要求"解封后从 0 开始"，所以触发时清空窗口。否掉。
- **按会话（群）计数**。同一个人在 10 个群里各刷 3 条就绕过去了；按 QQ 全局计数（跨群跨私聊共用）才是"这个人刷太快"。
  代价：在 A 群刷满会连带影响 B 群，属于有意为之。
- **持久化静默状态**。窗口是秒级的，重启比窗口还慢，写盘只会带来"重启后莫名还在静默"的误导。运行态留在内存，
  只写一份 `silenceLive` 快照回配置给设置页显示。否掉。

## Consequences

- 计数口径必须**在"真的会执行"之后**才记：权限不足（当普通消息放行）、被冷却吞掉、协议端重推的重复 `messageId`
  都不算；执行失败与超时**算**（确实占了执行链）。这条口径写进了 `test/command-gateway-silence-test.mjs`。
- 两条白名单落在两张已有的表上：权限表每行（含默认行）勾「不受次数限制」（这个人怎么用都不被静默）、
  指令表每条（含元指令）勾「不计入触发次数」（只管计数，静默期内仍然会被拦）。
- 表现上"认领 + 同一静默期只提示一次"：被拦的尝试会写进「最近调用」（原因 `静默中` / `无指令权限`），
  但不刷新静默期；静默期内**普通聊天完全不受影响**（静默只在指令链上生效）。
- 权限 -1 与静默是两道**独立**的门，先判 -1：`-1` 的人不需要被静默就能一直拦，且只提示一次。
- 运行态：`src/config.js` 里只多一个 `silenceLive` 快照（设置页只读清单）；真正的 `Map` 在内存里，重启即清零。
