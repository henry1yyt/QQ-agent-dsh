# 群黑名单：闸门放调用点入口、只吞指令尝试，拦截链连带不可见

群黑名单（按群的指令关闭开关）+ 白名单（全局豁免名单）要回答三个口径问题：

1. **闸门放在哪** —— `command.dispatch` 调用点入口最前（先于本插件组装的拦截链），还是只放在
   自己解析指令的 `dispatchSelf` 那一步？
2. **被挡的指令长什么样** —— 静默吞掉（`handled: true`，无回执），还是照「权限不足」的先例放行当普通消息？
3. **白名单豁免到哪** —— 只免群黑名单这道闸，还是连带提升指令权限？

我们决定：**闸门放入口最前**；黑名单群里非白名单用户的消息根本不进拦截链——
像指令的被**静默吞掉**（记一次「最近调用」，原因「群黑名单」，无回执），不像指令的照常放行当普通聊天；
**白名单（全局一份）只豁免群黑名单这道闸**，用户在黑名单群里放行后走完整链路，权限等级照旧在后面算。

与京玉版指令前置（jy-2.1.0-Beta，docs/adr/0012）同口径，这是同一决策在补丁架构上的移植。

## Considered Options

- **入口整体拦截（选定）**。语义干净：「这个群的指令系统整个关了」。隐私模式的触发词（`/隐私模式`）
  本质也是指令，"任何人使用指令不会生效"就该把它一并算进去；实现上也是一个 if 的事。
  代价（有意接受）：黑名单群里 privacy-mode 没法开会话，已开的会话会断——消息不再交给它。
- **只挡 `dispatchSelf`**。拦截链在黑名单群里照常工作，privacy-mode 还能用。
  否掉：作者最初的直觉就是这条，拷问后改选整体拦截——「只挡自家指令」读起来像实现细节而不是需求。
- **被挡指令放行当普通消息（权限不足先例）**。代价：模型会**看见** `/帮助` `/禁言 @张三` 这些原文，
  可能接一句「我不能禁言人哦」——对发送者来说这算一种「生效」，还诱导继续试。
  管理员拉黑一个群，多半就是不想让群里的人玩指令，所以这里不走「当没看见」，走「-1 无指令权限」的先例：吞。
- **白名单按群一份**。在 A 群加的白只惠及 A 群，语义最收敛；但管理走设置页（见下），按群维护要挨个群抄群号，
  而作者拍板的全局白名单语义（"这几个是我自己人，哪儿都能用"）更贴合实际信任关系。否掉。
- **名单用指令管理（`/群黑名单`）**。运行时顺手，但作者明确要纯设置页管理——群号抄写这类操作交给
  可视化选择器（走核心 `/api/onebot/groups|friends`）更不容易错。

## Consequences

- 拦截链成员（privacy-mode 等）在黑名单群里**收不到任何非白名单用户的消息**——这是口径决定的，
  不是 bug；拦截者作者不需要为此做任何事，但文档（本 ADR 与 CONTEXT.md）必须把这个连带后果写明。
- 黑名单群是**默认拒绝**：拿不到发送者 QQ 的消息按"非白名单"算，指令照吞。与 `silenceExempt`
  "拿不到 QQ 宁可放行"的口径相反——那里放行的代价只是少拦一个刷子，这里放行的代价是关不掉一个群。
- 白名单用户在黑名单群里也要过权限等级、静默、冷却那一整套——白名单不是通行证，只是不被
  群黑名单这道闸拦住。权限表每行照常可以填 -1 把某个白名单用户在全局禁掉。
- 名单存设置（`groupBlacklist` / `userWhitelist`，`[{ id, name? }]`，纯数字 id、去重），
  改动即时生效（settings() 每条消息现读）；设置页表格是唯一写入口，无管理指令。
- 被拦的尝试不进任何会话与存档（`handled: true`），只留「最近调用」一条记录，方便看出谁还在试。
